## Problem

زیرساخت برنامه‌ها و سرویس‌های داخلی شرکت به روشی تکرارپذیر برای آماده‌سازی سرور، استقرار و عملیات نیاز دارد. تغییر دستی روی میزبان‌ها، بازسازی محیط را دشوار و تشخیص تنظیمات واقعاً مستقرشده را مبهم می‌کند.

این پروژه تعریف زیرساخت، jobهای استقرار و مستندات عملیاتی شرکت را در Git متمرکز می‌کند و برای لایه پلتفرم و سرویس‌ها اتوماسیون مشترک دارد.

## System Design

پلتفرم فعلی از Ansible برای آماده‌سازی میزبان و کلاستر، Docker Swarm برای ارکستریشن، GitLab CI برای جریان استقرار و Traefik برای ingress و TLS استفاده می‌کند. تعریف stack و job هر سرویس در Git نگه‌داری می‌شوند و لایه برنامه و زیرساخت مشترک را پوشش می‌دهند.

سرویس‌ها شامل GitLab و runnerها، Harbor و رجیستری آرتیفکت، PostgreSQL و PgBouncer، Redis/Sentinel، MongoDB، MinIO، ابزارهای همکاری و برنامه‌های داخلی هستند. Prometheus، Grafana، Alertmanager، Loki و Promtail لایه مانیتورینگ و لاگ را تشکیل می‌دهند. NFS و volumeهای پایدار برای سرویس‌های stateful استفاده می‌شوند.

مخزن جداگانه زیرساخت RKE2، برنامه‌های Kubernetes را با `app.yaml`، مقادیر Helm، manifest اختیاری و اسکریپت استقرار مشترک استاندارد می‌کند. پیکربندی Traefik، GitLab، Harbor، Rancher، NFS، Longhorn و bootstrap مربوط به Argo CD در این مسیر قرار دارد.

## Architecture Decisions

- تعریف زیرساخت و جریان استقرار در Git نگه‌داری می‌شود تا تغییر قابل بررسی و ردیابی باشد.
- playbookهای Ansible راه‌اندازی Docker Swarm، اتوماسیون سرور و همگام‌سازی گواهینامه را انجام می‌دهند.
- templateهای GitLab CI مراحل مشترک و دسترسی استقرار را فراهم می‌کنند؛ تنظیمات هر سرویس در stack و job خودش می‌ماند.
- Traefik لایه مشترک مسیریابی است و ذخیره‌سازی پایدار مستقل از چرخه عمر کانتینر مدیریت می‌شود.
- secret وارد مقادیر Helm نمی‌شود و از متغیرهای CI یا مسیر مدیریت secret تنظیم‌شده تأمین می‌شود.
- استقرار RKE2 با توصیفگر مشترک سرویس، انتخاب chart، تنظیمات محیطی و hook اختیاری قبل از استقرار استاندارد می‌شود.

## Tradeoffs

پیاده‌سازی فعلی به سبک GitOps است: تنظیمات در Git و اجرا از مسیر CI انجام می‌شود. برخی jobهای همگام‌سازی و استقرار RKE2 دستی آغاز می‌شوند؛ بنابراین reconciliation پیوسته برای کل زیرساخت ادعا نمی‌شود. bootstrap مربوط به Argo CD در مسیر Kubernetes وجود دارد.

اتوماسیون مشترک تکرار کار را کم می‌کند، اما تغییر در ingress، storage و زیرساخت استقرار مشترک نیازمند کنترل اثر تغییر است. هر سرویس stateful به روش مستقل بکاپ، replication و بازیابی نیاز دارد؛ موفقیت استقرار کانتینر به‌تنهایی بازیابی‌پذیری دیتابیس را ثابت نمی‌کند.

## Production Behavior

زیرساخت و سرویس‌های داخلی شرکت بر این پلتفرم قرار دارند و از تعریف‌های نسخه‌بندی‌شده و jobهای مشترک استقرار استفاده می‌کنند. استقرار stackها مستقل انجام می‌شود، تاریخچه pipeline قابل بررسی است و مانیتورینگ و لاگ وضعیت سلامت سرویس‌ها را نشان می‌دهند.

مسیر RKE2/Helm همین مدل عملیاتی را با ساختار یکسان برنامه و نقطه ورود مشترک استقرار گسترش می‌دهد تا سرویس‌های Kubernetes در کنار زیرساخت Swarm وارد چرخه عملیات شوند.
