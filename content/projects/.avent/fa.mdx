## Problem

سفارش فروشگاه و حسابداری باید یک فروش واحد را نمایش دهند. ورود دوباره سفارش در ERP، کار تطبیق ایجاد می‌کند و احتمال فاکتور جاافتاده یا تکراری را بالا می‌برد. Avent چرخه سفارش را به حسابداری متصل می‌کند تا مشتری، اقلام، تخفیف و روش پرداخت فروش مستقیماً وارد ERP شوند.

## System Design

سامانه از دو سرویس Go تشکیل شده است: API فروشگاه با Gin، GORM، PostgreSQL، Redis و MinIO و ERP حسابداری با chi، sqlc، pgx و PostgreSQL. مسئولیت‌های دامنه‌ای جدا هستند و ارتباط از API مشخص یکپارچه‌سازی فروشگاه انجام می‌شود.

فروشگاه ورود OTP موبایل، کاتالوگ، سفارش، رزرو موجودی، پرداخت، ارسال و مدیریت را پوشش می‌دهد. ERP کدینگ حساب‌ها، فاکتور فروش، سند حسابداری، ثبت در دفتر و گزارش‌های مالی را مدیریت می‌کند.

### Order-to-Accounting Flow

1. مشتری سفارش را ایجاد و پرداخت را در فروشگاه تکمیل می‌کند.
2. اطلاعات سفارش پرداخت‌شده با شناسه ثابت سفارش، مشخصات مشتری، اقلام، تخفیف و روش پرداخت به ERP ارسال می‌شود.
3. ERP سفارش را به فاکتور فروش و سند حسابداری متناظر تبدیل می‌کند.
4. ارسال دوباره همان شناسه سفارش، فاکتور قبلی را برمی‌گرداند و فاکتور جدید نمی‌سازد.

همگام‌سازی محصول endpoint مستقل دارد. لغو فاکتور نیز عملیات صریحی است که فاکتور مرتبط با سفارش و سند حسابداری آن را حذف می‌کند.

## Architecture Decisions

- منطق خرید و حسابداری در سرویس مسئول خود قرار دارند و قرارداد API مرز ارتباط آن‌هاست.
- شناسه سفارش فروشگاه، هویت عملیات ساخت فاکتور است؛ تکرار درخواست باعث ساخت فاکتور تکراری نمی‌شود.
- معنای روش پرداخت حفظ می‌شود؛ تسویه درگاه یا بدهکاری مشتری بر اساس روش پرداخت ارسالی و تنظیمات ERP ثبت می‌شود.
- تخفیف کوپن در اقلام فاکتور لحاظ می‌شود و هنگام تبدیل سفارش از بین نمی‌رود.
- درخواست‌های یکپارچه‌سازی با API key احراز هویت می‌شوند و عملیات فاکتور به کاربر عامل مرتبط است.
- داده تجاری در PostgreSQL نگه‌داری می‌شود و ERP دسترسی SQL نوع‌دار دارد؛ Redis و MinIO نیازهای cache و ذخیره‌سازی اشیای فروشگاه را پوشش می‌دهند.

## Tradeoffs

تفکیک سرویس‌ها توسعه مستقل هر دامنه را ممکن می‌کند، اما ارتباط شبکه‌ای به مسیر فروش تا حسابداری اضافه می‌شود. idempotency از ثبت تکراری جلوگیری می‌کند؛ به‌تنهایی تضمین تحویل در قطعی طولانی ERP نیست. وضعیت سفارش و فاکتور باید برای تطبیق قابل بررسی باشد.

صحت حسابداری به کدینگ، نگاشت مشتری و محصول، نوع تسویه و توزیع تخفیف وابسته است. این اطلاعات بخشی از قرارداد یکپارچه‌سازی هستند و صرفاً برای نمایش استفاده نمی‌شوند.

## Production Behavior

یکپارچه‌سازی ERP سفارش پرداخت‌شده را می‌پذیرد، در درخواست تکراری همان فاکتور را برمی‌گرداند و عملیات ایجاد یا به‌روزرسانی محصول و لغو فاکتور دارد. سفارش فروشگاه بدون ورود دستی دوباره، در ERP به فاکتور و سند حسابداری تبدیل می‌شود؛ دو سرویس در کنار هم یک جریان تجاری واحد می‌سازند.
